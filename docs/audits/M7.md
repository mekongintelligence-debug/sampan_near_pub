## Notes and fix direction
- **M7-01:** fetch `depositTx` and require it final, with the gate's `funded` event for `core.mandate_hash` in a successful receipt (the checker's M6-06 rule). Otherwise refuse, or write `null`.
- **M7-02:** refuse when `dtx.transaction.hash` (and `mtx.transaction.hash`) is present and differs from the requested hash.
- **M7-03:** refuse unless `input.gate === core.gate`, so that events are taken only from the gate the core names. The author's test constant `GATE = "gate.testnet"` then has to become the vector's gate. That corrects a fixture; it does not weaken a test. Consider checking `token` against `mandate.asset` too.
- **M7-04:** collect every candidate and keep the one whose hash equals `core.order_hash` (or `core.mandate_hash`). Wrap format errors from candidates so they are skipped, not thrown.
- **M7-05:** take an optional order selector (`orderId` in the test) and pick the event whose `order_id` matches it. Without a selector, keep "exactly one". Match the order by hash as in M7-04.
- **M7-06:** also require `p.mandate_hash === core.mandate_hash`. The author's `payoutLog` helper then needs the field the real gate emits.
- **M7-07:** treat a non-object status as "not successful" (`typeof s !== "object" || s === null || "Failure" in s`).
- **M7-08:** re-run `pnpm e2e` with the current code once the testnet mandates allow it. Commit the clean results. Record the registration transaction hashes so the mandate side can be re-packed by anyone. Correct "e2e re-run" in the threat review, or point it at that run. Say in the e2e header and README that the testnet "direct checkout" is a buyer-sent payment, not 1Click.
- **M7-09:** either drop the gate hint, or state it as what it is: one more guess, useful only on an RPC that ignores the sender. Update the checker README and the not-found detail. The mainnet residual risk stays as an **Assumption** until the first mainnet direct checkout is checked with a mainnet RPC.
- **M7-10:** add a Rust unit test: gate configured `network: "mainnet"`, testnet mandate, expect `wrong_network`. Keep the audit's checker control as the regression for the receipt direction.
- **M7-11:** say "every decision on an authenticated order", name the 1Click-supported chains or say "many chains", and note that testnet receipts show "Cannot verify" by design (Q16) until mainnet.
- **Threat review, other notes.** M7-CR3 (final, successful registration) is harmless but not a control: the mandate is bound by its signature and hash, so the source transaction's status does not matter. "Huge inputs": the packer decodes every function-call argument in the transaction, and the e2e's `fetchTx` reads the RPC answer with no size cap (the checker caps at 4 MB). That is acceptable for an operator script. Add a cap if the packer is ever run on user-supplied hashes.

## Residual risk and accepted items
- No packer finding can make a wrong receipt green. Every envelope is re-checked by the checker against the chain. The packer's gaps give red or "Cannot verify" for correct decisions, or block packing.
- The M7 checker change does not alter any M6 guarantee. The hint only adds one more `tx` lookup. Signer, executor, events, finality and gate-key checks are unchanged (controls in `apps/checker/src/audit-m7.test.ts`).
- **Assumption:** mainnet RPCs, like testnet, return a transaction for any sender. If not, a 1Click-sent direct checkout is "Cannot verify", never green.
- **Assumption:** a 1Click delivery to the gate is one transaction whose receipts include the token's `ft_transfer_call` with `receiver_id` = gate and the order in `msg`. Shown only with synthetic data (`pack.test.ts` M7-CR1).
- Mainnet examples (one release, one refusal) do not exist yet. They need the person-run mainnet deploy and purchase.
- Testnet only. No key material was used or read. Read-only RPC queries only. `scripts/m7/e2e.mjs` was not run.
