### Notes on findings
- **M0-01.** gitleaks (8.24.2, default rules, the repo config) misses an `ed25519:<base58>` secret in each of these: a near-cli credentials JSON (`private_key`), `NEAR_PRIVATE_KEY=…`, a quoted `export …_SECRET_KEY="…"`, and a TS constant. The end-to-end test copies the M0 controls into a scratch repo, adds `agent.sampan.testnet.json` with `git add -A`, and commits. The file is not ignored (M0-03), the hook passes, the commit succeeds, and a later `gitleaks detect` over the history finds nothing. This is the key type of the environment's testnet secret, of every `near` CLI login and, later, of mainnet keys. A clean gitleaks run therefore does not support the "secrets scan clean" claim needed before publishing (section 3.6, section 6 M8-M9). The existing test "gitleaks finds a planted fake private key" uses an RSA PEM and does not pass the repo config (`-c`), so it could not have caught this. Rated High, not Critical, because policy (3.5) keeps mainnet keys out of sessions and CI, so the immediate exposure is a testnet key.
- **M0-02.** The `.gitleaks.toml` comment says "No allow-list yet". gitleaks still honours an inline allow marker on any line and a `.gitleaksignore` file at the repo root, and it does not decode base64 (`--max-decode-depth` defaults to 0) or open archives. The control check in the test confirms that the same key is found when it is in plain form.
- **M0-05.** `CLAUDE.md` says that contract refusals must not panic and there must be no `unwrap()`, and the threat review cites clippy for this. Each of these probes passed `make clippy`: a function-level `#[allow(clippy::unwrap_used)]`; `near_sdk::require!`, `assert!`, slice indexing, `unreachable!` and `env::panic_str` (none are covered by `clippy::panic`); and an unwrap under `#[cfg(target_arch = "wasm32")]`, which is caught only when clippy is run with `--target wasm32-unknown-unknown`. The control check confirms that a plain unwrap is rejected. This is defence in depth for M3; it does not affect behaviour at M0.
- **M0-08.** These are the guards meant to stop "a later change silently weakening" the baseline. Each test runs the real baseline test, filtered by name, on a copied tree with one weakening applied. The control check confirms that the unmodified copy passes.
- **M0-13.** I checked that both ignored advisories (RUSTSEC-2026-0387 crypto-bigint, RUSTSEC-2024-0449 unsafe-libyaml) reach the project only through `near-sdk` `unit-testing` → `near-vm-runner` / `near-parameters`. Those crates are not built for wasm32 even with dev edges included, so neither advisory reaches the deployed contract today. Without the ignores, `cargo audit` reports exactly these two and nothing else. A failing test is not possible at this commit; the finding records that the guard will not scale as written.
