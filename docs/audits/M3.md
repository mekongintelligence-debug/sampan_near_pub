### Notes and fix direction (not applied)
- **M3-01:** take an order in `msg` only when that same call creates the mandate, never on a top-up, and require `order.amount <= amount` of this transfer. Consider requiring that the order's ID equal the mandate nonce (a single direct-checkout order per mandate) and that `max_amount` equal the order amount for agentless mandates (FORMATS.md 3 calls it the "exact price (person)"). A front-runner who learns the signed mandate before it is funded (for example from the 1Click quote or the widget) can still fund it first. Tie the first funding to the buyer's own order, or document this as an **Assumption** for M5.
- **M3-02 / M3-05:** bound storage in NEAR, not only in record counts. Options: at `new`, refuse caps whose worst-case storage (measured per-record maxima × caps) exceeds the free balance; release a mandate slot (and its receipts' storage) after refund once expiry plus a margin has passed, keeping only the nonce key and receipt hashes for replay protection; or make `min_funding` partly non-refundable to cover storage. Either way, add a test that registers many mandates and checks that the contract's balance cannot be drained (SECURITY.md 3.1 "Storage").
- **M3-03:** pay registrations only for payees, or only once per mandate, from a per-mandate allowance. Alternatively, register `refund_to` and the payee at funding time, when a failure can simply return the deposit. Do not count already-registered accounts (check `storage_balance_of` first, or release the slot when the deposit comes back).
- **M3-04:** make `new` `#[private]` and also check `predecessor == current_account_id` in the body, so unit tests see it. Deploy and initialise in one batch transaction (`deployContract` + `functionCall("new")`). Have the script compare `get_config` with the intended config and stop on any difference.
- **M3-06:** decide the in-message order before the funding is committed. If the result is an unanchored refusal, return the full amount, keeping CR3 in mind. Alternatively, anchor every direct-checkout outcome, including gas.
- **M3-07:** add `mandate_hash` and `order_hash` (both grammar-checked) to `refused` events when they are known and the caller is authorised.
- **M3-08:** treat any `PromiseResult::Successful` as success. Read the result with `promise_result_checked(0, 0)` and match on `Err(Failed)` versus `Err(TooLong)`, or check only that the promise did not fail.
- **M3-09:** in `parseEnvelope`, require R1, R2, R4 and R5 to pass, and require observed < order amount when R7 fails. Both are statements about gate v1 behaviour, so record them in FORMATS.md 6 if adopted.

### Items checked with no finding
- **Token origin:** `ft_on_transfer` compares `predecessor_account_id` with the configured token before parsing anything. A fake token gets the full amount back and no state is written (`pc_fake_token_credit_refused`; testnet A2).
- **State before promises:** in `decide` and `refund`, all balances are computed with checked arithmetic and written before the transfer promise is created. The gas check sits after the expensive work and before the writes. The `#[private]` callbacks also re-check the predecessor in the body. `restore` puts back exactly the amount taken, into the bucket it came from, and the receipt is never overwritten (`payout: Failed`).
- **Interleaving:** a release, then a refund at expiry, then a failed payout callback leave `funded = spent + escrow + refunded` and `total_escrow = Σ escrow`, and the restored amount can be refunded again (`purchase_racing_refund`, `pc_payout_failure_after_refund_keeps_totals_consistent`). Top-ups are impossible after expiry, so a refund can never race a funding. Escrow ≤ remaining budget is an invariant, which keeps the `observed` semantics sound.
- **NEP-141 batch:** `storage_deposit` (registration deposit, `registration_only: true`) and `ft_transfer` (exactly 1 yocto) go to the token in one receipt, so the batch is atomic and the deposit returns to the gate on failure. The callback reads exactly one result.
- **S1 and S2:** every `ft_transfer` the gate creates goes to the stored `payee` (release) or `refund_to` (refund). Both come only from a verified signed mandate. Amounts are bounded by R7 and the escrow (`pc_refund_by_stranger_pays_only_refund_to`, `pc_agent_mandate_rejects_order_in_message_and_strangers`). M3-01 does not change the destination or the cap.
- **Replay:** network, gate and asset are checked at funding. The nonce key is buyer plus nonce (CR1), and receipts are keyed by mandate plus order ID (CR2), so neither can be squatted across mandates. Order replay is refused without state.
- **No panics in user-reachable contract paths:** every refusal returns a value. Only near-sdk's own argument decoding and its non-payable check can panic, which is acceptable because no state is written. Clippy `forbid` covers unwrap, expect, panic, indexing and arithmetic, and the banned lint covers `env::panic_str` and `env::abort`.
- **No untrusted text in logs or state:** events hold static reasons, hex hashes, decimal amounts and the canonical receipt core (re-parsed before it is emitted). `sender_id` is never stored or logged.
- **Receipt core vs FORMATS.md 6:** closed object, R1 to R9 in order, decision equal to "all pass", positive `block_height`, canonical bytes, and the hash equal to the stored anchor (`pc_receipt_core_matches_formats_section_6`). The TypeScript checker accepts all 10 gate-produced receipt shapes (cross-language check in Method).
- **`hex_lower` made public** in `sampan-formats`: pure, total, no new behaviour.
- **Script:** testnet only (`assertTestnet`), the key is read from the environment and redacted in logs, the agent key is limited to `gate-m3.purchase` and always deleted in `finally`, and the buyer's mandate key is fresh for each run. Apart from M3-04, no issue found. The Makefile adds `wasm-release` (MVP features, stripped) and `testnet-m3`, and puts the gate into `coverage` and `mutants`.

## Author's open items and "decision" items: auditor's view
- **M3-CR3 (refused funding returns to `sender_id`, i.e. 1Click):** agree that it stays open and is significant. It is reachable without any bug: a 1Click delivery that lands at or after expiry, one that exceeds `max_amount` because someone topped up the published mandate first (M3-01), or one that hits a cap (M3-02, M3-05). Each sends the buyer's money to 1Click's refund flow, not to `refund_to`. Verify where 1Click returns it in M5, and prefer fixes that reduce funding refusals for agentless mandates.
- **M3-CR6 (unanchored refusals write no state):** agree for unauthenticated requests (unknown mandate, invalid order, R5 stranger), where writing state would be the storage griefing vector. The CLAUDE.md hard rule ("refusals must … write state") then needs the lead's written exception and a README note. Partly disagree for refusals of *authorised* callers (`no_escrow`, `order_cap`, `insufficient_gas`, the agent's own R4 replay): at least make their events attributable (M3-07).
- **M3-CR8 (registrations counter counts already-registered payees):** the bound is fine, but the counter is a lifetime budget that strangers can spend (M3-03). Accepting CR8 is reasonable only once M3-03 is fixed.
- *Decision* **Unanchored refusals:** as for CR6 above.
- *Decision* **Storage (Q17 as built):** disagree as built. The bounds are lifetime record caps that any stranger can consume at zero net cost, and they are not tied to the balance that pays for them (M3-02, M3-03, M3-05).
- *Decision* **Failed payout:** agree. The budget and escrow are restored exactly, the order ID stays used, and the receipt shows `Failed`. M3-08 is the one edge where a success could be read as a failure.
- **Direct checkout (as built, not marked decision):** disagree as built (M3-01, M3-06). The 1Click message-size and gas **Assumption** remains for M5.
- **No admin or upgrade methods:** agree, but `new` must be protected (M3-04).
- **Observed values / M3-X1:** agree. The change is correct for every receipt the gate can produce (10 of 10 accepted); M3-09 is optional tightening.
- **Tests on the mocked VM instead of near-workspaces:** acceptable for unit and property tests. It leaves SECURITY.md 3.1's callback-gas proof and section 5's sandbox kind unmet (M3-11). Either add one sandbox or testnet step at minimum gas, or record the decision.
