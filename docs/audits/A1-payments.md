### Notes and fix direction (not applied)
- **A1P-01:** choose an attribution that fits in 1,024 characters and keeps the A1P-02/A1P-03 properties.
  - Option 1, mandate registered first. The buyer (or a relayer, or the widget through the buyer's NEAR account) submits the signed mandate to the gate before paying, with a storage deposit or within the reserved caps. The 1Click message is then only `{"mandate_hash":"<64 hex>"}` (about 85 characters), plus at most an `order_id`.
  - Option 2, derived order. For agentless mandates, derive the single order from the mandate (exact price = `max_amount`, one item, `order_id` = `nonce`), so the message is the signed mandate alone. This still exceeds 1,024 for long mandates, so the widget would have to cap mandate size, and test that cap against the limit.
  - Option 3, escrow first (Q12 option 3). Rejected for human checkout unless EVM buyers get a way to spend, such as `agent` = a NEAR account they control.
  - Whichever is chosen, add a vector or test that the largest mandate the widget can produce fits in 1,024 characters, and re-run a dry quote with that exact message.
- **A1P-02:** for any delivery that carries a mandate validly signed for this network, gate and asset, never hand the amount back to `sender_id`.
  - Credit what fits in the mandate's escrow.
  - Send any excess, or the whole amount when the mandate cannot be created (expired, caps, nonce used), straight to the mandate's `refund_to` in the same call, or keep it in a refund-only bucket that anyone can flush to `refund_to`.
  - Keep returning to `sender_id` only when the message is unreadable or the signature fails, since then no `refund_to` is known.
  - Combine this with an anchored, attributable event, and take care that the refund-only path cannot be used for storage griefing (cap it by the reservation logic).
  - Also verify with 1Click (Q20 contact) what happens to an `ft_transfer_call` refund, and record the answer.
- **A1P-03:** make a later delivery with the same mandate succeed rather than bounce. Accept an order on a top-up when it is the mandate's derived single order (see A1P-01 option 2) and still unused; otherwise credit the top-up to escrow. Alternatively, with mandate pre-registration (A1P-01 option 1), only the registered mandate's hash travels, so there is nothing new to front-run. Do not rely on `min_funding` size as the defence.
- **A1P-04:** let refunds pay `refund_to`'s registration even after the payee's was paid. The per-mandate reservation already counts one registration, so reserve two. Alternatively, register `refund_to` at funding time, when a failure can still return the deposit.
- **A1P-05 / A1P-06:** compare the whole live `quoteRequest` with the request sent (deep equality), and bound `quote.minAmountOut`, `quote.deadline` and `amountIn`. Require a mixed-case EIP-55 address, or a second confirmation of the address in checksummed form.
- **A1P-07:** write down both bounds. Use `mandate.expiry_ns ≥ quote deadline + settlement margin` (for example 30 minutes for EVM origins), and make the checkout's mandate expiry short (for example a few hours), so a refused payment is refundable soon. Show both times to the buyer.
- **A1P-08:** decide where `refund_to` comes from for each wallet type, and show it to the buyer before signing. The widget should check with a final-finality RPC view that the account exists, and refuse to proceed otherwise. State it in the README.
- **A1P-10:** add a gate test that funds and decides a mandate signed with ERC-191, using a direct checkout and a refund, so that path runs before mainnet.
- **A1P-09:** in the widget, rebuild the expected quote request from the mandate the buyer signed, and refuse to show a deposit address unless the 1Click response echoes it exactly: `recipient` = gate, `recipientType` = `DESTINATION_CHAIN`, `destinationAsset` = `nep141:` + the configured token, `customRecipientMsg` byte-equal, `swapType` `EXACT_OUTPUT`, `amount` = price, `refundTo`/`refundType` as the buyer chose, `deadline` within bounds, no `appFees` unless intended, `dry` false. Ask NEAR for the quote-signature key and payload (Q38); until then, document the gap. Show the mandate hash next to the deposit address, so the receipt can be matched later.

## Edge cases checked against docs/SECURITY.md section 6 (M5)
- [ ] 1Click quote errors and timeouts: `packages/payments` is not built. `mainnet-quote.mjs` fails safe on an error status (no deposit address), but uses no timeout and prints the server's `message` verbatim. Add a timeout and print only a sanitised reason in M5.
- [ ] Expired quotes: not checked (A1P-05 `quote.deadline` case).
- [ ] Changed rates between quote and deposit: EXACT_INPUT varies the delivered amount, which leads to over-max bounces or R7 refusals (A1P-02, A1P-07). M5 must use EXACT_OUTPUT.
- [ ] Refunds from 1Click: before delivery, 1Click refunds to `refundTo` (ORIGIN_CHAIN). After a gate refusal, the refund goes to 1Click (A1P-02; behaviour undocumented, **Assumption**).
- [ ] Quote deposit address or recipient tampered by page script: not built (A1P-09).
- [ ] Widget with a wrong SRI hash, in a hostile frame, `postMessage` from a foreign origin: not built.
- [ ] Mandate shown differs from the signed payload: not built.
- [x] Dry-quote path never signs or sends anything: `oneclick-dry-quotes.mjs` sends 7 requests, all to `/v0/quote` with `dry: true`, and reads no key ("control: the dry-quote script sends only dry quotes …"). The person-run script asks for a live quote only after the exact typed phrase ("control: … only after the typed confirmation").

## What M5 and the person-run mainnet steps must enforce
Contract and design (before the first mainnet purchase):
1. A1P-01 to A1P-04 fixed with their tests passing; A1P-07 and A1P-08 decided in writing.
2. Attribution message ≤ 1,024 characters for the largest mandate the widget can produce, re-checked with a dry quote carrying that exact message.

## Items checked with no finding
- **Token origin before parsing:** `ft_on_transfer` compares `predecessor_account_id` with the configured token first; a fake token gets the full amount back with no state and no promise.
- **No state before the last check in `fund`:** every refusal returns before the first write. The only refusal after writes (`order_not_decided`) undoes them exactly, and the unanchored `decide` paths write nothing and create no promise. So the gate never keeps state for an amount it returns, and never returns an amount it has credited.
- **`sender_id` is untrusted:** it is ignored, never stored or logged, and attribution depends only on the signed mandate in `msg`.
- **Destinations:** every `ft_transfer` goes to the stored payee or `refund_to`, both from a verified signed mandate; an order cannot name a new destination (R8). Amounts are bounded by escrow and the remaining budget.
- **Batch shape against USDC mainnet:** `storage_deposit {account_id, registration_only: true}` with `registration_deposit` (config range 0.00125-0.1 NEAR; USDC's bounds are exactly 0.00125, and the excess is refunded under `registration_only`), then `ft_transfer` with exactly 1 yocto, in one receipt (atomic). USDC uses 6 decimals, like the mock token, so amounts in mandates match 1Click's base units for NEAR USDC.
- **Failed payout:** budget and escrow are restored once; a replayed or foreign callback changes nothing (in-body predecessor check plus `#[private]`).
- **Refunds:** go only to `refund_to`, anyone may trigger them after expiry, and the refund includes `refund_to`'s registration when the mandate's registration is unused.
- **Dry-quote script:** dry only, no key, placeholder recipient, no deposit address.
- **Person-run quote script:** holds no key; 2 USDC cap; mainnet-only recipient grammar; mixed-case EIP-55 checked; the typed phrase binds amount, recipient and refund address; recipient and refund swaps in the live quote are refused.
- **`safety.mjs`:** testnet-only guards and key redaction (unchanged since M1; not used by the 1Click scripts, which need no key).

### One design change for both A1 audits
The lead chose two options on 7 November 2026: registration by a small Sampan relayer, and a one-way stop.
- **Register first.** `register_mandate(signed_mandate)` is payable. Whoever calls it (the Sampan relayer, or the buyer) attaches a deposit of `reservation_per_mandate()`: (2,400 + orders × 450) bytes of storage plus two token registrations. With 16 orders that is about 0.0985 NEAR. Any surplus goes back at once. A refused registration (stopped, bad signature, wrong network, gate or asset, expired, `lifetime_too_long`, `already_registered`, `nonce_used`, `mandate_cap`, `deposit_too_small`) returns the whole deposit, writes no mandate and emits `registration_refused`.
- **Payments name the mandate.** `FundingMsg` is `{"mandate_hash": …, "order": …}` or `{"signed_mandate": …, "order": …}`, with exactly one of the two. Only a zero amount, an unreadable or oversized message, an invalid mandate or an unknown mandate hands the payment back to the sender. Every other payment to a registered mandate is kept. What fits in escrow (the budget left, the per-mandate cap and the total cap) goes to escrow. The rest becomes **refund due**, payable to `refund_to` at any time. Nothing goes to escrow once the mandate has expired or the gate is stopped.
- **Unsigned orders inside a payment** (agentless mandates only) must ask for exactly `max_amount` and are released at most once per mandate (`not_exact_price`, `already_paid`). An order is never decided unless this payment put money in escrow. After the decision, this payment's escrow (all escrow, once released) moves to refund due. An order sent to an agent mandate is ignored (`order_ignored`) and the payment stays in escrow for the agent.
- **Lifetime.** `Config.max_lifetime_ns` (1 hour to 30 days, 24 hours on mainnet) bounds `expiry - now` at registration.
- **Closing.** A mandate closes once it has expired and holds no escrow, refund due or pending transfer. The registrant gets back the deposit minus the bytes it leaves behind (receipts and registered-account entries, counted in `kept_bytes`) and the registrations it used. The gate never pays for a stranger's storage.
- **Stop.** `Config.guardian` (optional) may call `stop()` once. After it, registrations and purchases are refused (`stopped`), payments to existing mandates are kept for the buyer, and refunds and callbacks work as before. Nothing can undo it, and it moves no funds. Calls from anyone else get `not_guardian`. On mainnet the guardian is a named person's hardware wallet, never the deploy key.
- **Init** is `#[private]` and refuses a network that does not match the account suffix.

Interface changes made several auditor tests call `register_mandate` before paying. Each of these mechanical changes is marked "Author adaptation after the A1 redesign" in the test file, and no assertion was weakened. Where a test asserted a reason that moved to registration (for example `wrong_network`), it now asserts that reason at registration, and `unknown_mandate` for the payment.
