Goals: S7 (testnet key, Telegram token), S3 (Gate 2 evidence) and S1/S2 for the person-run mainnet quote script (amount, recipient, refund address).

Method:
- Read `docs/SECURITY.md`, the M1 section of `docs/MILESTONES.md`, `docs/audits/M1-threat-review.md`, `docs/gates.md` and `CLAUDE.md`. Then read every M1 file line by line.
- Checked near-api-js 7.3.1 (`lib/index.js`, `lib/rpc-errors`). The Gate 2 rejection messages map from the RPC node's `InvalidTxError` variants. They are not client-side checks, so the protocol did reject B–G. The library has no `console.*` call on the paths the spike uses. `inspect()` of an `Account` or `KeyPair` shows the secret in two unprefixed base58 forms (`secretKey`, `extendedSecretKey`).
- Re-ran `gate2-spike.mjs` once on testnet (accounts under `sampan-trust-01.testnet`). Its output contained none of the key (checked by substring). B–G failed for exactly the reasons listed in `docs/gates.md`. H, and also the re-run's `init gate`, failed with the same bare `WebAssembly trap: An 'unreachable' opcode was executed`. A re-run therefore reports `1 unexpected outcome` (see M1-10).
- Sent three extra **dry** 1Click quotes and no live one. The API echoes `customRecipientMsg` in `quoteRequest` and validates its type and length. It rejects unknown properties with 400. So "accepted" in the Q12 table means validated, not silently ignored. Responses carry a `signature` field.
- Ran the scripts as child processes with `fetch` or `near-api-js` replaced by mocks. These runs used no network and a fake key. Ran `scripts/secrets-scan.sh --history`, `--dir spikes` and `--dir scripts`: no leaks. Searched the working tree (outside `node_modules`/`target`) and the full git history for the real testnet key, without printing it: not found. `lint-banned`: no findings.
- `mainnet-quote.mjs` was **not** run live. Its tests use a mocked `fetch` that refuses any host other than 1Click and never reaches the network.

Exploit tests: `scripts/m1/audit-m1.test.mjs` (vitest, 21 tests). Each test asserts the required behaviour, so it **fails while its finding is open**. At the audited commit, all 21 fail and the existing `safety.test.mjs` passes 5/5. `make check` (test-web) is therefore red; that is intended. When a finding is fixed, its tests become the regression tests named after its ID.

## Edge cases checked against docs/SECURITY.md section 6
Section 6 lists no edge cases for M1. Threat-review controls checked:
- [x] Key read only from `NEAR_TESTNET_PRIVATE_KEY`, held in memory, never written to disk: holds (`safety.test.mjs`; no `fs` writes in M1 scripts).
- [ ] Error messages pass through redaction: partial (M1-02, M1-08).
- [x] Testnet guard (network, `.testnet` accounts, RPC allow-list) runs before any call: holds for `gate2-spike.mjs`. Network and RPC are constants there, so only the account check does real work. The 1Click scripts hit the mainnet API by design: `oneclick-dry-quotes.mjs` cannot override `dry: true` (the spread puts `base` first, and no variant sets `dry`).
- [ ] Agent key deleted at the end of every run: not on abort (M1-09).
- [x] Gate 2 B–G rejected by the protocol: confirmed by re-run and by the near-api-js error mapping. The script's own pass/fail is not evidence (M1-01).
- [ ] Mainnet script: dry by default and typed confirmation present, but the confirmation does not bind the refund address or the live quote (M1-03, M1-04, M1-05, M1-07).

## Residual risk and accepted items
- `scripts/post-audit.mjs`: no token leak found. The URL is never in an error, network errors are replaced with a fixed string, and `e.message` has the token removed. Telegram's `description` is printed raw: untrusted text to the terminal, Info only.
- In the spike, every sub-account (including `agent`) holds the parent's **full-access** key. Gate 2 used a separate fresh function-call key, so the result stands. For M4 the agent account itself must hold no full-access key that the agent can reach. Otherwise S3 does not hold in the demo setup.
- The spike contracts are throwaway (`spikes/gate2/README.md`) and were not audited as production code. The gate's `purchase` pays any payee and amount the agent names. M3 must not start from it.
- 1Click is trusted for the deposit address (out of scope per section 2). M1-03 narrows but cannot remove that trust.
