### Notes and fix direction (not applied)
- **M6-01:** give each `KnownGate` the facts a stranger needs, and check them. (1) For gates that claim to be locked (mainnet): `view_access_key_list` at `final` must be empty, and the entry should record the height `lockedSince` from which the account held only the reviewed code and no key. Then a receipt is green only if `core.block_height > lockedSince`. After a lock the reviewed code can neither deploy nor add keys, so the state cannot change afterwards. Pin `lockedSince` from the deploy and lock transactions, which a person verifies once (archival `view_account` and `view_access_key_list` at that height). (2) For gates with a key (testnet): never plain "Verified". Show "Cannot verify: the operator of this test gate can still change it", or a clearly different amber verdict, as the lead decides, and state it in the README. (3) Also reject a decision transaction whose actions include `DeployContract` or whose signer is the gate. That is cheap defence in depth, but it does not replace (1).
- **M6-02:** reject a second RPC on the same host (or the same operator) as the primary. Run the *whole* chain read on both RPCs (chain ID, code hash, config, access keys, stored record, transaction with finality, event content, block height and timestamp) and compare the full `ChainView`. ### Items checked with no finding
- **Look-alike contract and other accounts with the same code:** the gate must be an exact, listed account (`KNOWN_GATES`, exact string match), and the signed mandate binds `gate`. Another account running the reviewed code, or a look-alike, is "Not valid" (M6-CR1 tests). Account IDs follow an ASCII-lowercase grammar (`packages/mandate/src/grammar.ts:7`), so Unicode homoglyphs cannot occur. ASCII look-alike payees are what the buyer signed (out of scope, SECURITY.md section 2).
- **Pinned build:** the pinned code hash equals the live gate's and reproduces from the audited source (A1, `51dac1d`, no contract change since). The token is pinned and read back from `get_config` at `final`.
- **Receipts for a different order or mandate:** `get_receipt(mandate_hash, order_id)` comes from the envelope. Its `core_hash` must equal the file's, and the core binds `mandate_hash` and `order_hash` (which includes `order_id`). The event must match both `core_hash` and `order_id`. A swapped real decision transaction is red (author test).
- **Events in other receipts of the same transaction:** only receipts executed by the gate with a non-failure status count, matched on `core_hash` and `order_id`. Other gate events (`payout`, `refused`, `funded`) are ignored. The block of *that* receipt gives height and timestamp.
- **Finality and reorgs:** views use `finality: "final"`, the transaction uses `wait_until: "FINAL"`, and the checker requires `final_execution_status === "FINAL"`. The block is fetched by hash from a final transaction. Non-final data, errors, garbage and a wrong chain ID are "Cannot verify" (author tests). A second RPC on another network is "Cannot verify".
- **Release versus refusal:** the stored decision and `core_hash` must both match. A release needs `payout: Done` (`Pending` gives unknown, `Failed` gives red). A refusal needs `None`. Expiry is checked against the gate's block time for releases.
- **Sender lookup:** the sender is used only to find the transaction. Every security property comes from the event and the stored record, so a wrong or missing sender can only give "Cannot verify". The README states the direct-checkout limit as an **Assumption**.
- **File checks and S6:** `parseEnvelope` is strict (size before parsing, numbers rejected, closed objects, hashes recomputed, signature, pure rules R6/R8/R9 and the R7 budget, observed values, R1/R2/R4/R5 must pass). The only free text, `agent_note`, is length-capped, has no control or bidi characters, is outside the checks, and is rendered with `textContent`.
- **CSP and build (built output inspected):** `default-src 'none'`; `script-src` and `style-src` by sha256 of the exact inlined content (which matches); `connect-src` exactly the four RPC origins from `rpc.ts`; `img-src`, `font-src`, `object-src`, `base-uri`, `form-action` all `'none'`. No `<!--` in the script, `</script` escaped before hashing, replacement functions used for script and style (no `$` pattern risk). No `innerHTML`, `eval`, `new Function` or other URL in the bundle. Nothing is loaded at runtime: no CDN, fonts or images. The meta CSP comes before the style and script. `dist/` is git-ignored and rebuilt by `make check`.
- **Network and leakage:** the page contacts only the configured RPC(s), with `credentials: "omit"`, `referrerPolicy: "no-referrer"`, `cache: "no-store"` and a `no-referrer` meta tag. A `#r=` fragment is never sent anywhere. A link cannot choose the RPC. The RPC operator learns the mandate hash, order ID, transaction hash, agent, `refund_to` and the buyer's implicit account. That is inherent to checking against an RPC, and only allow-listed hosts receive it.
- **Hostile RPC answers:** streamed 4 MB cap (M6-CR7), every chain-derived step inside one guard that gives "Cannot verify" (M6-CR2), a non-array view result gives "Cannot verify", and the event log is capped at 16 KB.
- **`capture-fixtures.mjs`:** read-only views. It reads `.secrets/m4-state.json` (not read by this audit) only for the public signed mandate and the agent account. It scrubs transaction signatures, and writes fixtures only if the live check verified. The fixtures hold public data only (public keys, the hex NEP-413 signature).
- **Makefile, package.json, CI:** `build-checker` joins `check`. `esbuild 0.28.2` and `playwright 1.63.0` are pinned exactly. CI installs Chromium for the page tests, which `make test-web` (vitest over `apps/**`) runs. `pnpm audit` is clean. Note: no TypeScript type check runs anywhere in `make check`. That is pre-existing and not M6-specific.
